# Аналитическая спецификация

## Проблема, пользователи и границы

Обращения из разных каналов теряются, сроки не контролируются, отчётность собирается вручную. Пользователи: оператор поддержки (создаёт и ведёт заявки), специалист (исполняет), руководитель (смотрит сводку), администратор стенда (эксплуатирует). В границы входят backend, PostgreSQL, Swagger, тесты и локальное развёртывание; не входят UI, авторизация, уведомления и интеграции с внешними каналами.

## User Stories и acceptance criteria

- **US-01 / FR-01.** Как оператор, я создаю заявку. AC: обязательные title/category/priority/dueAt; существующая категория; серверные id/time; NEW; HTTP 201.
- **US-02 / FR-02.** Как сотрудник, я получаю и редактирую открытую заявку. AC: GET 200/404; PATCH меняет только description/priority/dueAt; терминальная заявка даёт 409.
- **US-03 / FR-03.** Как сотрудник, я меняю статус. AC: разрешён только заданный граф; RESOLVED/CANCELLED не открываются; запись и история атомарны; RESOLVED получает closedAt.
- **US-04 / FR-04.** Как оператор, я ищу заявки. AC: все фильтры комбинируются; пагинация максимум 100; сортировка только по разрешённым полям; поиск title без учёта регистра.
- **US-05 / FR-05.** Как руководитель, я получаю отчёт `[from,to)`. AC: единая выборка; распределения; просроченные открытые; среднее секунд для RESOLVED либо null; неверный период даёт 400.
- **US-06 / FR-06.** Как аудитор, я вижу историю. AC: только существующая заявка; порядок changedAt ASC/id ASC.
- **US-07 / FR-07.** Как администратор, я запускаю сервис воспроизводимо. AC: Compose ждёт healthy DB; Flyway; persistent volume; readiness.
- **US-08 / FR-08.** Как администратор, я резервирую и восстанавливаю данные. AC: custom-format dump; восстановление в отдельную БД; проверочный SQL.

## Функциональные требования

FR-01…FR-08 определены выше. **FR-09:** единый безопасный ответ ошибок 400/404/409/500. **FR-10:** категории возвращаются через GET. **FR-11:** просрочка означает `dueAt < now` и статус NEW/IN_PROGRESS. **FR-12:** конкурентное изменение не должно молча перезаписываться.

## Нефункциональные требования

- **NFR-01:** Java 21 и реальный Kotlin/JVM в одном Spring Boot монолите.
- **NFR-02:** PostgreSQL, Flyway, `ddl-auto=validate`, индексы и ограничения.
- **NFR-03:** воспроизводимость ARM64/AMD64; без пользовательских абсолютных путей.
- **NFR-04:** health/readiness, graceful shutdown, секреты вне исходников.
- **NFR-05:** модульные, PostgreSQL-интеграционные и E2E-тесты; внедряемый Clock.
- **NFR-06:** документированный API и понятная учебная архитектура.

Ограничения: один сервис, без frontend; CI/CD окончательно проверяется только после подключения GitHub/runner; rollback требует обратно совместимых миграций.

## Контракты и примеры

`POST /api/tickets` принимает `{"title":"VPN","description":"Ошибка","categoryId":4,"priority":"HIGH","dueAt":"2030-01-01T12:00:00Z"}`. `PATCH /api/tickets/{id}` принимает любое непустое сочетание изменяемых полей. `PATCH .../status`: `{"status":"IN_PROGRESS"}`. Список: `/api/tickets?status=NEW&priority=HIGH&categoryId=4&title=vpn&overdue=false&page=0&size=20&sort=createdAt,desc`. История, категории и отчёт описаны в Swagger и `requests.http`. Ошибка имеет поля `timestamp,status,error,message,path,fieldErrors`.
